1. Summary

Counselor NIDS watches the traffic on a network interface and raises an alarm when a connection looks like an attack. It is built to solve a practical problem: machine-learning detectors that work in the lab usually fail once installed on a real organisation's network, and this system lets them adapt to that network by themselves, using a signature engine the organisation already runs. Two independent checks judge every connection:

  • Three machine-learning detectors, each a specialist in one family of attacks: floods (DoS), break-ins (password guessing and website attacks) and botnets. When a detector is unsure, it asks the others for advice. This is the counselors network of Quincozes et al. (2019).
  • Snort 3, a widely used signature engine that recognises known attack patterns inside the traffic.

Every Snort alert is linked to the connection it belongs to and compared with the AI's verdict on that connection, so each incident is reported as Confirmed (both agree), Disputed (Snort only) or AI only. A web dashboard shows the incidents, who is attacking, how the detectors reached their decisions, how many false alarms the system raises on the network over days, and whether every part of the system is running.

On real attack traffic it never trained on, the system catches 99-100% of most attack types, including floods, password guessing and botnet traffic, with almost no false alarms (Section 8). The thesis extension (Section 9) adds Snort as a counselor, self-learning from agreement between Snort and the AI, and adaptive trust, so the detectors can adapt to a network they were never trained on without anyone labelling its traffic.

2. The problem and the thesis objectives

The real-world problem: the deployment gap. Machine-learning intrusion detectors score almost perfectly on the dataset they were trained on, but lose most of that accuracy on a different network. Trained on CIC-IDS2017 and tested on CSE-CIC-IDS2018, published classifiers fall to about chance accuracy (Cantone et al., 2024) — a macro-F1 near 0.12. Every real deployment is a "different network", so in practice an organisation's new detector either misses real attacks or buries its security team in false alarms. This is the main reason AI-based detection is not trusted in the field.

The problem in practice

A small company installs an ML-based IDS. In the vendor demo it caught 99% of attacks. On the company's own network it drowns its two-person security team in false alarms and misses a real intrusion. The company has no labelled data from its network and no ML specialists. Today their only realistic choice is to turn the ML off and trust Snort alone.

Two things make this hard to fix in the field, and both shape the design:

  • Nobody can label a live network's traffic. Supervised retraining needs labelled examples of that network's own normal and attack traffic, which almost no organisation has.
  • Most organisations have no ML expertise to retrain or tune a detector even if they could.

Almost every organisation already runs a signature engine (Snort), whose rules behave the same on every network. This project uses that existing, network-independent tool as a built-in teacher, so the detectors adapt to the organisation's own network on their own — no labelling, no ML expertise, no vendor.

General objective

To design, implement and evaluate a counselor-based network intrusion detection system in which a signature-based IDS (Snort) guides machine-learning detectors to adapt to a network they were never trained on, without labelled traffic from that network — so that the detector can be deployed on a new organisation's network and become accurate there automatically.

Specific objectiveThe real-world challenge it addresses
1. Snort as a counselorIn the counselors network, detectors only ask other AI detectors, who can share the same blind spots on a new network. Snort's signatures behave the same on any network, so they give independent advice — cutting the false alarms and missed attacks that overwhelm a small team.
2. Learning from agreementThere are no labels on the new network. Connections where Snort and the AI independently agree serve as labels for free, so the detector recovers the accuracy lost to the deployment gap, and a safety gate blocks retraining that hurts or makes the detectors forget what they knew.
3. Adaptive trustEach counselor's trust is measured once, in the lab. It is re-estimated on the new network from how often the others agree with it — so rules that misfire on this network are down-weighted — for every Snort rule, and (tested as an ablation) for the AI detectors themselves.
4. Cross-network evaluationThe mechanisms are evaluated by training on one lab (CSE-CIC-IDS2018) and deploying on another (CICIDS2017), in both directions, against each baseline — the evidence that adaptation to a genuinely unseen network is real, not the end in itself.
5. Zero operator effort, run liveThe operator labels nothing and needs no ML expertise: the system adapts itself and only asks for the occasional verdict. Research detectors rarely run on live traffic; this one does, and the practical obstacles found along the way are documented.

Technical note

All services communicate through Redis streams: nids:unknown (new flows), nids:inbox:<detector>, advice request and reply lists, nids:alerts and nids:snort:alerts, a flow index (sorted sets keyed by connection and by host pair), and a nids:health hash of heartbeats. Because each part is a separate process, any one can crash and restart without stopping the others.

4. The AI detectors and the counselors network

How one detector decides (from the paper)

  1. Training (Algorithm 1). Five classifiers are trained: naive Bayes, three kinds of decision tree (J48-like, REPTree-like, RandomTree-like) and a random forest. The evaluation data is grouped into clusters with K-Means. For every cluster, the most accurate classifier, and any within 0.1% of it, is kept.
  2. Detection (Algorithm 2). A new connection is placed in its nearest cluster, and that cluster's selected classifiers vote. If they agree, that is the verdict. If they disagree, there is a conflict.
  3. Counselors. On a conflict, the detector asks the other detectors (its counselors) for their verdict on the same connection. It takes the advice of the most confident counselor, if that counselor's accuracy is at least 90%.

Extensions made in this project

  • Cross-check. A detector cannot raise a conflict about an attack family it never learned; it is just confidently wrong. So every "normal" verdict is also checked with the counselors, and a confident "attack" advice overrides it.
  • Unresolved conflicts count as normal. When the classifiers disagree and no counselor can help, the paper falls back on the best classifier's guess. On live traffic those guesses caused most false alarms while accounting for almost no real detections, so they are treated as normal.
  • Connection-only flows skip the AI. Port scans and failed connections exchange no data. The detectors never learned them and only produced guesses (one scan caused ~50,000 false alarms), so they are left to Snort.

5. Snort alongside the AI

Snort 3 runs on the same interface with the project's 42 rules (snort/rules/nids.rules) and the ~4,000 Snort 3 community rules. Each alert is linked to its connection: the same two addresses and ports, the same protocol, and a time inside the connection's start-to-end window. A port-scan alert stands for many probes, so it is linked to every connection between the two hosts within ±30 seconds. The detectors are then asked for their verdict on that connection, using the same advice request they use with each other.

AgreementMeaning
ConfirmedSnort and the AI both say attack: very likely real.
DisputedSnort says attack, the AI says normal: a possible Snort false alarm, or an attack the AI never learned (for example SQL injection, which looks like ordinary web traffic to the AI).
AI onlyThe AI flagged a connection Snort had no alert for: typically floods and botnet traffic.

Rules and tuning

  • Website attacks: SQL injection (UNION SELECT; a quote followed by an AND/OR comparison; ORDER BY probing; information_schema), cross-site scripting (<script, event handlers, javascript:) in the URL or a form, and website login brute force (20 password posts from one source in 60 s).
  • FTP and SSH brute force over a wide 120 s window, so slow guessing paced to slip under a short-window threshold is still caught. SYN and HTTP floods are covered by rate thresholds, port scans by Snort's scan inspector.
  • Checksums are not checked. Network cards fill checksums in themselves (offloading), so a machine's own outgoing packets look broken to Snort, which used to drop them. Until this was fixed, Snort raised no website-attack alert at all on the 2018 website-attack capture.
  • Quieted rules: protocol-anomaly alerts are off, and informational community rules (pings, ICMP errors, 1-minute DNS TTLs, UPnP discovery) are suppressed. They fired ~3,800 times on a normal workstation.

7. Training the detectors

Key finding

Detectors trained on the published dataset CSVs caught 0% of password-guessing attacks measured the live way. The CSVs were made with the Java CICFlowMeter; live capture uses the Python cicflowmeter, and the two differ in 71 of 154 feature medians (packet lengths with or without headers, flag counting, where flows are split). So the detectors are trained on the datasets' raw packet recordings, measured by the same flow meter as live capture. This also means the known labelling errors in the CICIDS2017 CSVs (Engelen et al., 2021; Lanvin et al., 2023) do not reach training: flows are labelled from the packets and the published schedule, not the CSVs.

  1. Fetch: single hosts' captures from the CSE-CIC-IDS2018 archive (about 1.3 GB, using HTTP range requests, out of 40-60 GB archives).
  2. Label: the attack windows are found in the packets themselves, and each flow is labelled by its attacker-victim pair. The dataset's CSV timestamps can't be used: they're a 12-hour clock without AM/PM.
  3. Measure: the Python flow meter, reading recordings by their own clock (Section 12 explains the bug this fixed). Snort also runs on every slice, and the rules that fired are kept with each flow.
  4. Split by time: within every attack type and capture, the earliest 80% of flows train and the latest 20% test, so test flows come from later in the attack than anything learned.
  5. Promotion gate: the installed detectors are tested on the same test flows. New ones replace them only if false alarms don't rise and no attack type drops by more than 2 points. Model files are pickles, which run code when loaded, so the installed set is listed with SHA-256 checksums that live mode verifies before loading.

9. The thesis extension: Snort-guided adaptation

9.1 Snort as a counselor

The counselors network now accepts advisors: counselors that give advice but classify nothing themselves. Snort is one. When a detector's classifiers disagree on a connection (a conflict), Snort's verdict on the same connection is advice like any other, worth the trust of the most trusted rule that fired. Snort only ever says "attack", and only on connections it alerted on: silence is not evidence of normal traffic, since Snort cannot see floods or botnets.

  • Conflicts only. Snort does not take part in cross-checking confident "normal" verdicts. In development runs that turned the system into "AI or Snort", inheriting every Snort false alarm (27% of normal connections, mostly Windows policy rules).
  • A trusted "attack" wins. On a conflict, the most trusted "attack" advice beats any "normal" advice. Otherwise the flood detector, which knows nothing about website attacks, could confidently overrule Snort on one. This is the same "limited vision" reasoning as the cross-check.

9.2 Learning from agreement

While the detectors watch a new network, each chunk of traffic produces agreement labels:

  • attack: Snort alerted and the AI says attack without Snort's advice (so Snort cannot confirm itself);
  • normal: Snort is silent and every detector is unanimously sure the connection is normal.

Everything else stays unlabelled. Each detector stays a specialist: it learns "attack" labels only for connections it was involved in (it said attack, or was unsure), and every detector learns the "normal" labels. A retrained detector replaces the old one only if:

  1. it is at least as accurate on a held-back fifth of the agreement labels; and
  2. it has not forgotten: on the original lab's labelled test data, no attack type it knew drops by more than 2 points and false alarms don't rise. Without this check, retraining on mostly flood labels made the break-in detector lose website attacks.

No label from the new network is used.

9.3 Adaptive trust

  • Snort rules (in the proposed system): each rule's trust is a Beta estimate (prior 0.9, worth 20 observations), raised when the AI independently agrees and lowered when every detector is sure the connection is normal. In development runs, the Windows RDP policy rule fell to 0.02 trust after the AI contradicted it 786 times, while the attack rules rose to 0.996-0.9998.
  • AI detectors (ablation): each cluster's accuracy, its advice confidence and optionally its choice of classifiers, re-estimated from agreement labels with the lab value as a prior worth 200 samples. This turned out harmful. Agreement labels are the easy cases every classifier gets right, so the estimates are biased upwards: re-selecting classifiers let weaker ones vote (more false alarms, fewer website attacks caught), and inflated confidence let "normal" advice win cross-checks it should lose. Agreement can safely re-weight Snort's rules, but not the AI's own classifiers.

9.4 The experiment

scripts/live_detectors/adapt.py trains the detectors on one lab and streams the other lab's traffic through the system in time order, in chunks. A fixed test set (the target's latest 20%) is scored before adaptation and after every chunk. It compares:

It reports detection rate, false-alarm rate, per-attack detection and a balanced score at every step, each rate with a 95% Wilson confidence interval; McNemar's test for every comparison with the deployed system and the baselines (is the difference real or chance?); how many agreement labels each chunk produced and how many were right; the final trust of every Snort rule; and a blind-spot analysis (per attack type, Snort's coverage against the change in detection, so a drop on an attack Snort cannot see is caught).

Status

All three mechanisms and the experiment harness are implemented. The cross-network results use the CICIDS2017 packet captures (about 50 GB); the builder for that data also runs Snort on every day automatically, and reads the captures directly (pcapng supported). Results will be added when the bidirectional runs complete.

9.6 In live mode

The mechanisms also run in the live system. Whenever Snort runs, the detectors start with --snort-counselor; NIDS_SNORT_COUNSELOR=0 turns it off.

  • Linking: the Snort bridge links each alert to its connection as soon as the connection is known.
  • Waiting for Snort: a detector that is unsure waits until Snort has seen that connection to the end (at most 10 seconds), then takes its advice.
  • Rule trust: adapts from Confirmed and Disputed verdicts, and is kept in logs/snort-trust.json between runs.
  • Fair disagreements: a disagreement counts against a rule only if the AI flagged nothing from the alert's source. Without this, the Challenge-ACK rule, which catches the Slowloris connections the AI misses, lost all its trust (0.095); with it, the rule keeps 0.97, while the noisy Windows policy rules still drop to 0.09 and 0.36.

On the held-out recording, the live services with Snort as a counselor caught 47% of Slowloris, against 35% without, with no false alarms (community rules on, live adaptive trust). Offline, with fixed trust, the same recording reaches 69.5%. In full-speed replays, how many doubts Snort settles varies between runs, because the services race each other; live traffic arrives in real time.

9.7 Learning from the analyst's verdicts

On a real home network the lab-trained Flood detector flagged about 2% of connections. All of them were long-lived HTTPS and push connections, whose tiny keep-alive packets look like slow DoS. Snort's agreement cannot fix what Snort cannot see, so the person watching closes the loop.

  • Mark: any alarm can be marked Not an attack or Real attack. The verdict is saved with the connection's measurements (detectors keep those of flagged connections for 7 days) and takes the alarm out of the counts at once. It also counts for or against any Snort rule that fired on that connection.
  • Teach: the detectors retrain on the verdicts. A retrained detector is installed only if it gets the marked connections more right and has forgotten nothing: overall, in every cluster holding lab attacks, and for every attack type.
  • Switch: running detectors switch to it within a minute, once it matches its checksum. A changed model without a matching checksum is never loaded.

On the 2018 lab, the normal connections the Flood detector wrongly flagged went from 4 to 0, while lab detection moved from 99.99% to 99.98%. The safety check rejected a retrain that would have cost the Break-in detector website attacks (94.2% → 90.9%).

11. Deployment, operations and security

  • One command: ./start.sh setup, then ./start.sh live wlan0 (or en0 on macOS), or ./start.sh --prod live wlan0 for production servers. It also runs in containers with docker compose up, Snort included.
  • As services: sudo deploy/install-systemd.sh wlan0 installs one systemd unit per part. Each restarts on failure, and the detectors restart with capture so two runs never mix.
  • Nothing runs as root: capture and Snort get only CAP_NET_RAW and CAP_NET_ADMIN.
  • Health: every service sends a heartbeat. The dashboard shows one chip per part, and nids health runs every minute from a timer.
  • Logs: the system journal under systemd. Under start.sh, logs over 20 MB are rotated. The alert journal keeps one year, and Snort rule trust is kept in logs/snort-trust.json.
  • Security: httpOnly SameSite=Strict session cookies; a custom header on every state-changing request as a CSRF guard; at most 10 login attempts a minute per client. In production the API refuses to start without a real secret key, and it sends security headers. Model files are checksum-verified before loading, and the Redis instance is bound to loopback.

12. Limitations

  • The detectors learned from one lab family (CIC) with one attacker per attack type. This is exactly the problem the thesis extension tackles; the demonstrated generalisation is within the CIC dataset family, and a structurally different network is future work. Until then, check false alarms on your own network with the journal.
  • The botnet detector knows one botnet family (Ares). There is no live DDoS or infiltration detector yet; DDoS comes with the 2017 data.
  • Slowloris detection varies with the attack's phase (35-85%).
  • Website attacks rely mainly on Snort: the AI had only about 200 website-attack flows to learn from. These rules need visible HTTP payloads, so they do not apply to encrypted (HTTPS) traffic; flow-level detection of floods, scans and botnets still works over TLS.
  • Snort-guided adaptation can only use Snort's help for attacks Snort can see. For floods and botnets it depends on the AI detectors agreeing with each other.
  • Adversarial robustness and sustained throughput are not evaluated, and a long-run live false-alarm measurement on a production network is future work.
